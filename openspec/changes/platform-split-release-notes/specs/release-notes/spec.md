## ADDED Requirements

### Requirement: A release note states which platform it is about

`frontend/app/assets/js/changelog.js` SHALL be the source of user-facing release
notes, and every version's entry SHALL be keyed by platform rather than being a
flat list.

Three states SHALL be distinguishable, because they mean different things:

| Value | Meaning |
| --- | --- |
| a non-empty list | what changed on that platform |
| `[]` | that platform shipped no change in this release |
| key omitted | that platform did not exist for this release |

A platform's absence SHALL NOT be used to mean "no changes". One version number
ships the extension and the Android app, and silence is otherwise ambiguous
between "nothing changed" and "nobody wrote anything" — which is what made
`ReleaseNotes.kt` show its generic fallback for releases that did have something
to say.

Prose SHALL NOT carry the distinction. It was previously stated inside the note
text — "Bu sürümde eklentide bir değişiklik yok. Android uygulamasında ..." —
which requires the reader to parse a sentence to find out whether the release
concerns them.

#### Scenario: A release that changed only one platform

- **WHEN** a version's entry lists app changes and an empty extension list
- **THEN** both platforms are represented, one with its changes and one with an explicit statement that nothing changed

#### Scenario: A release from before the app existed

- **WHEN** a version predating the Android app is rendered
- **THEN** no Android section appears at all, because nothing is being claimed about it

### Requirement: Every surface shows every platform's section

The extension's welcome page and the app's sürüm notları screen SHALL each render
all of a version's platform sections, not only their own.

A user on one platform still wants to know the other got the fix. It is the same
release, and showing only half of it makes the two clients look as though they
have diverged.

Each surface SHALL lead with its own platform, because the first question either
reader is asking is what changed for them.

No rendered section SHALL be empty. A platform with nothing to report SHALL
render one line saying exactly that, and an unknown version SHALL render a single
unlabelled fallback line. A caller that had to handle emptiness would have to
decide what to render, and every caller would decide it separately.

#### Scenario: The extension page leads with the extension

- **WHEN** the welcome page renders a version with both sections
- **THEN** the extension's section appears first, followed by the app's

#### Scenario: The app screen leads with the app

- **WHEN** sürüm notları renders a version with both sections
- **THEN** the app's section appears first, followed by the extension's

#### Scenario: An unknown version does not render blank

- **WHEN** a version with no entry is rendered
- **THEN** a single generic line is shown, because a release must never be blocked on someone writing a note

### Requirement: The Android copy cannot drift from the source

`ReleaseNotes.kt` SHALL mirror `changelog.js`. It SHALL NOT be generated: doing
so would couple the Android build to the `frontend/` tree, which is otherwise out
of scope for Android work.

Because the two are hand-maintained statements of the same release in two
languages that cannot import each other, a test SHALL assert that for the version
recorded in `android/version.json`, every platform section matches `changelog.js`
word for word — and that neither file lists a platform the other does not.

Only the shipping version SHALL be compared. Backfilling the whole history would
turn a wording fix on an old note into a build failure, which is not what this
protects.

#### Scenario: A note edited in one file only

- **WHEN** the shipping version's text is changed in `changelog.js` but not in `ReleaseNotes.kt`
- **THEN** the unit test fails, naming the platform whose notes differ

#### Scenario: The shipping version has notes

- **WHEN** the version in `android/version.json` has no entry
- **THEN** the unit test fails, because users would see the fallback

### Requirement: The website's release notes are generated, never hand-written

`docs/changelog.json` SHALL be generated by `npm run changelog` from
`changelog.js` and `docs/changelog.legacy.json`, and SHALL NOT be edited by hand.

`npm run check` SHALL fail when it is stale, so a note added without regenerating
is caught before release rather than shipping a site that disagrees with the
extension about what the release contained. Hand-maintenance is what left the
page frozen at 2.6.0 while four Ekşi Engel releases and every 0.1.x went
unpublished.

Each note SHALL be emitted with its platform as a badge — `[Eklenti]`,
`[Uygulama]` — reusing the page's existing badge mechanism.

`docs/changelog.legacy.json` SHALL hold the pre-rename Ekşi Engel releases and
SHALL be appended verbatim. Those entries SHALL NOT be migrated into
`changelog.js`: they are a different numbering and a different format, and
folding English badge-formatted text into a Turkish user-facing data file would
degrade both.

The two lists SHALL be concatenated and SHALL NEVER be sorted together. The
project renamed and restarted numbering at 0.1.0, so "newest first" and "highest
version first" stopped being the same ordering — 3.2.0 is older than 0.1.2, and
any version comparison of the two says the opposite. Each list is already
newest-first on its own.

`docs/changelog.txt` SHALL NOT gain new releases. It is an archive of the
original development log and its TODO backlog, and SHALL say so at the top.

#### Scenario: A note added without regenerating

- **WHEN** `changelog.js` is edited and `npm run check` runs
- **THEN** it fails with an instruction to run `npm run changelog`

#### Scenario: The site shows the whole history

- **WHEN** the release notes page loads
- **THEN** it lists the 0.1.x releases newest-first, followed by the Ekşi Engel releases down to 1.0.0

### Requirement: A release is published to the website by being dated

Each version's entry MAY carry a `date`. An entry without one SHALL be excluded
from `docs/changelog.json`.

Notes are written while a release is still being built and `docs/` is a live
site, so listing an undated version would announce a release nobody can install.

`npm run version:*` SHALL stamp the date onto the version it bumps to, and SHALL
regenerate `docs/changelog.json`. Stamping SHALL happen at the bump rather than
at the tag, because bumping and tagging are separate acts in this project and
only the bump is guaranteed to happen exactly once. An entry that already carries
a date SHALL NOT have it moved.

`npm run release` SHALL include `changelog.js` and `docs/changelog.json` in the
release commit, so the committed tree passes its own `check`.

#### Scenario: Notes written ahead of the release

- **WHEN** an entry exists for a version that has not been bumped to
- **THEN** it does not appear on the website

#### Scenario: Bumping publishes it

- **WHEN** `npm run version:patch` bumps to that version
- **THEN** the entry is dated, `docs/changelog.json` is regenerated, and the release commit carries both
