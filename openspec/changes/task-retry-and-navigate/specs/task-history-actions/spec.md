## ADDED Requirements

### Requirement: Retry a task from İşlem durumu
The extension SHALL offer a "Tekrarla" action on any İşlem durumu task row
(queue table or completed table) whose stored record contains the original
per-target dispatch parameters (banSource, banMode, entryUrl, authorName,
authorId, targetType, clickSource, titleName, titleId, timeSpecifier). Clicking
it SHALL re-enqueue the task with those exact parameters through the same
background message path used for the original dispatch
(`background.js` message listener building a `wrapperProcessHandler` bound to
`processHandler`), regardless of whether the original task's status was
QUEUED, PROCESSING, COMPLETED, or FAILED. This requirement binds the extension
client only (Chrome and Firefox); there is no Android equivalent of this screen.

#### Scenario: Retry a FAILED task
- **WHEN** a task in the completed-tasks table has status FAILED and its stored
  record includes the original target parameters
- **THEN** clicking "Tekrarla" on that row enqueues a new task with the same
  banSource, banMode, entryUrl, authorName, authorId, targetType, clickSource,
  titleName, titleId, and timeSpecifier as the original

#### Scenario: Retry a COMPLETED (successful) task
- **WHEN** a task in the completed-tasks table finished successfully and its
  stored record includes the original target parameters
- **THEN** "Tekrarla" is available and behaves identically to retrying a FAILED
  task — the extension does not restrict retry to failures only

#### Scenario: Retry unavailable for tasks missing target parameters
- **WHEN** a task's stored record predates this feature or is a bulk/list-sourced
  task with no single per-target dispatch (e.g. date-based bulk action, muted-list
  block, list refresh)
- **THEN** the "Tekrarla" button is not rendered for that row

### Requirement: Navigate to a task's source from İşlem durumu
The extension SHALL offer a "Git" action on any İşlem durumu task row whose
stored record contains an entryUrl, authorName, or titleName/titleId. Clicking
it SHALL open the corresponding Ekşi Sözlük page (entry, profile, or title) in
a new browser tab via a direct URL, without depending on the target being
reachable through in-page search or listing. This SHALL work identically
whether or not the target user or title is currently blocked or muted by the
extension. This requirement binds the extension client only.

#### Scenario: Go to an entry-sourced task
- **WHEN** a task row's stored record has an entryUrl (task was dispatched from
  an entry dropdown menu)
- **THEN** clicking "Git" opens that entryUrl in a new tab

#### Scenario: Go to a profile-sourced task whose author is now blocked
- **WHEN** a task row's stored record has an authorName, and that author is
  currently in the extension's blocked or muted list
- **THEN** clicking "Git" still opens `{origin}/biri/{authorName}` in a new tab,
  unaffected by the author's blocked/muted status

#### Scenario: Go to a title-sourced task
- **WHEN** a task row's stored record has a titleName/titleId (task was
  dispatched against a title, e.g. TargetType.TITLE)
- **THEN** clicking "Git" opens the corresponding title page in a new tab

#### Scenario: Go to unavailable for tasks missing source identity
- **WHEN** a task's stored record has none of entryUrl, authorName, or
  titleName/titleId (e.g. a bulk/list-sourced task, or a pre-feature record)
- **THEN** the "Git" button is not rendered for that row

### Requirement: Retry clicks are distinguishable in telemetry
The extension SHALL send a distinct analytics event when the user clicks
"Tekrarla", separate from the analytics generated by the retried task's own
execution. This SHALL use a new `ClickType` value sent via the existing
`commHandler.sendAnalyticsData` mechanism, so retry-driven volume is visible as
its own entry in the backend's `ClickType`/`ClientAnalytic` admin views without
requiring a backend schema migration. This requirement binds the extension
client only; the backend accepts and stores whatever `click_type` string it
receives, per its existing open-lookup behavior.

#### Scenario: Clicking Tekrarla sends a retry-specific analytics event
- **WHEN** the user clicks "Tekrarla" on any task row
- **THEN** the extension calls `commHandler.sendAnalyticsData` with a
  `click_type` dedicated to the retry action, distinct from the `click_type`
  that would be sent for a fresh action of the same kind

#### Scenario: Retried task still produces its own outcome telemetry
- **WHEN** a retried task subsequently runs to completion (success or failure)
- **THEN** the backend records an `Action` row for that run exactly as it would
  for a first-attempt run of the same banSource/banMode/target, with no special
  "is a retry" marker required on the `Action` model itself
